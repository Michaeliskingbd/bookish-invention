MORE EXPLANATION ON OPENIDDICT..............................
Think of OpenIddict as the security system that issues and verifies identity tokens for your application.

Your application has two major authentication responsibilities:
1. Knowing who a user is.
2. Proving that identity to other parts of the application.
ASP.NET Core Identity and OpenIddict handle different parts of this process.
1. ASP.NET Core Identity — manages users
Identity handles the actual user accounts.

For example:
- Registering users.
- Storing user details in PostgreSQL.
- Hashing passwords before storing them.
- Checking login credentials.
- Managing roles such as Admin and Client.
- Handling password resets and email confirmation.
Think of Identity as your user management system.
2. OpenIddict — handles tokens
Suppose a user logs into your application.

Your backend needs a secure way to tell other parts of the application:

"This request belongs to an authenticated user."

OpenIddict handles the token side of that process.

It:
- Issues access tokens after successful authentication.
- Issues refresh tokens.
- Validates token-related requests.
- Manages OAuth 2.0 and OpenID Connect flows.
- Supports secure authentication across web and mobile applications.
Think of OpenIddict as your token and authorization server.
3. How they work together
Consider a user logging into your Library API.
1. User

Enters login credentials from web or mobile


2. ASP.NET Core Identity

Checks the user's credentials against the stored account


3. OpenIddict

Issues an access token and potentially a refresh token


4. Library API

Validates the access token before allowing access to protected endpoints


For example, the user sends this HTTP header when requesting their books:
GET /api/books
Authorization: Bearer eyJhbGciOi...


Your API validates the token. If it's valid, the API can identify the user and determine their permissions.
4. Why not just use Identity?
Identity alone is excellent for managing users, but it isn't a complete OAuth 2.0 / OpenID Connect authorization server.

You want both web and mobile clients. OpenIddict gives you standardized authentication flows, including Authorization Code Flow with PKCE, rather than requiring you to invent your own token protocol.
Remember this distinction
Technology	Responsibility
ASP.NET Core Identity	Who are the users?
OpenIddict	How are tokens issued and managed?
JWT access token	How does a client prove its authenticated identity to the API?
ASP.NET Core authorization	What is this authenticated user allowed to do?

One important distinction: OpenIddict does not automatically log users in or create their accounts. Identity manages accounts, and we'll build the login and authorization flow that connects Identity to OpenIddict.

That's the architecture we're building in LibraryApi.

Step 5 — Implement the registration method
Open AuthService.cs and add this method inside the AuthService class:

public async Task<IdentityResult> RegisterAsync(
    RegisterRequestDto request,
    CancellationToken cancellationToken)
{
    cancellationToken.ThrowIfCancellationRequested();

    var user = new ApplicationUser
    {
        UserName = request.Email,
        Email = request.Email
    };

    return await _userManager.CreateAsync(user, request.Password);
}



Let's understand the important parts
1. Creating the user
var user = new ApplicationUser
{
    UserName = request.Email,
    Email = request.Email
};


We use the email as the username for now.

Notice that we don't assign the password to the ApplicationUser object.

2. Creating the account
return await _userManager.CreateAsync(user, request.Password);


This is where Identity takes over.

Internally, Identity:
- Validates the password against your configured password policy.
- Checks username and email uniqueness according to its validators.
- Hashes the password using its password hasher.
- Persists the user through the configured Identity store.
- Returns an IdentityResult.
The password is never stored as plain text.

3. Cancellation token

ThrowIfCancellationRequested() checks whether the request has already been cancelled.

CreateAsync() itself does not accept a cancellation token, so cancellation cannot interrupt that operation once it starts.

Login authentication
We'll now implement login.

There is an important architectural distinction in your project:
- ASP.NET Core Identity verifies user credentials and manages user accounts.
- OpenIddict issues access tokens and refresh tokens.
We should use OpenIddict for token issuance rather than manually generating JWTs.

Our login implementation will eventually allow a user to authenticate and obtain tokens that can be used by both web and mobile clients.

Before implementing it, we'll examine how the OAuth 2.0 Authorization Code Flow with PKCE works, since that's the flow we've configured in OpenIddict.

Understand the login and token flow
Your application has three important components:
Component	Responsibility
ASP.NET Core Identity	Stores users and verifies passwords
OpenIddict	Handles OAuth 2.0 / OpenID Connect and issues tokens
Library API	Protects resources using validated access tokens

How authentication will work
We're using Authorization Code Flow with PKCE.
Authentication sequence
1. User opens the application
   
   A web or mobile client requests authorization.
2. OpenIddict receives the authorization request
   
   It checks the client and authorization parameters.
3. User authenticates
   
   If the user doesn't have an active login session, they are presented with a login interface. Identity verifies their credentials.
4. Authorization is granted
   
   The user approves the requested access where consent is required.
5. Authorization code is issued
   
   OpenIddict returns a short-lived authorization code to the client.
6. Client exchanges the code
   
   The client sends the code and its PKCE verifier to OpenIddict's token endpoint.
7. Tokens are issued
   
   OpenIddict returns the access token and, when requested and permitted, a refresh token.
8. Client accesses protected APIs
   
   The client sends the access token in the HTTP Authorization header.

Important: Why not simply create a /login endpoint that returns a JWT?
Because we're building an authentication server that supports both browser and native mobile clients.

Authorization Code Flow with PKCE provides a standardized approach without exposing user passwords to the client application.
Two concepts you need to understand
Access token: A credential presented to your API to prove the client's authorization.

Refresh token: A credential used to obtain a new access token without requiring the user to authenticate again, subject to the server's policies.

    LoginRequestDto request,
    CancellationToken cancellationToken)

    cancellationToken.ThrowIfCancellationRequested();

5. lockoutOnFailure: true enables Identity's configured account lockout behavior after repeated failed attempts.

Create the authorization controller

Create a new file:

Controllers/AuthorizationController.cs

Start with this code:
using LibraryApi.Models;
using Microsoft.AspNetCore.Identity;
using Microsoft.AspNetCore.Mvc;
using OpenIddict.Abstractions;
using OpenIddict.Server.AspNetCore;

namespace LibraryApi.Controllers;

public sealed class AuthorizationController : Controller
{
    private readonly UserManager<ApplicationUser> _userManager;
    private readonly SignInManager<ApplicationUser> _signInManager;

    public AuthorizationController(
        UserManager<ApplicationUser> userManager,
        SignInManager<ApplicationUser> signInManager)
    {
        _userManager = userManager;
        _signInManager = signInManager;
    }

    [HttpGet("~/connect/authorize")]
    [HttpPost("~/connect/authorize")]
    public async Task<IActionResult> Authorize()
    {
        var request = HttpContext.GetOpenIddictServerRequest()
            ?? throw new InvalidOperationException(
                "The OpenIddict authorization request cannot be retrieved.");

        var user = await _userManager.GetUserAsync(User);

        if (user is null)
        {
            return Challenge(
                IdentityConstants.ApplicationScheme);
        }

        var principal = await _signInManager.CreateUserPrincipalAsync(user);

        principal.SetScopes(request.GetScopes());

        return SignIn(
            principal,
            OpenIddictServerAspNetCoreDefaults.AuthenticationScheme);
    }
}


Understand the important parts
1. GetOpenIddictServerRequest()

Retrieves the authorization request that OpenIddict has already validated and passed to our controller.

2. GetUserAsync(User)

Retrieves the currently authenticated Identity user from the authentication cookie.

3. Challenge()

If the user isn't authenticated, the application requests authentication through the Identity cookie scheme. We'll connect this to our React login interface later.

4. CreateUserPrincipalAsync(user)

Creates a claims principal containing the user's identity and claims.

5. SetScopes()

Associates the requested scopes with the authenticated principal.

6. SignIn()

This is particularly important. We hand the principal to OpenIddict rather than generating tokens ourselves. OpenIddict takes responsibility for producing the authorization response.
Important limitation at this stage
This is our initial authorization endpoint. We still need to implement client registration, scope/resource validation, claim destinations, and the login redirect experience before considering the flow production-ready.
